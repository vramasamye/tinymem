# Memory-Systems Landscape Research (input to onememory ADRs + schema design)

Date: 2026-10-03. Scope: open-source AI-agent memory systems, against primary sources (arXiv papers, GitHub repos/READMEs, official docs). Every factual claim carries a source URL; conflicts and silences are flagged inline.

## Summary

- The 2025–2026 landscape converged on a shared shape: **typed memory layers + an explicit write pipeline (extract → resolve/dedupe → store) + hybrid retrieval + background consolidation**.
- **Mem0** defined the write-time ADD/UPDATE/DELETE/NONE loop — then in production (April 2026) largely abandoned UPDATE/DELETE at write time for single-pass ADD-only plus multi-signal retrieval-time fusion. https://github.com/mem0ai/mem0
- **Zep/Graphiti** defined bi-temporal validity (fact-truth vs system-knowledge timelines) and contradiction-as-invalidation-not-deletion. https://arxiv.org/abs/2501.13956
- **Letta/MemGPT** defined in-context memory blocks plus a background "sleep-time" agent that owns memory edits; its current coding agent stores memory as a git-backed filesystem (MemFS). https://docs.letta.com/letta-agent/memory
- **MIRIX** published the taxonomy closest to ours — six typed memory components with concrete per-type schemas — plus a per-type retrieval router (Active Retrieval). https://arxiv.org/abs/2507.07957
- **Memp** proved procedural memory distills into two granularities (steps + scripts) with explicit correction/deprecation and cross-model transfer. https://arxiv.org/abs/2508.06433
- **MemOS** contributed the lifecycle vocabulary (generation/activation/fusion/archive/expire, provenance, versioning, permissions); its activation/KV/parameter cubes are out of scope for an agent-side engine. https://arxiv.org/abs/2507.03724
- Storage is consolidating on **Postgres + pgvector** — Mem0's self-hosted server default, cognee's full-stack Postgres, memU's Postgres option. Strong validation for onememory's Postgres-first bet. https://docs.mem0.ai/open-source/overview
- Headline metrics are mutually contradictory (each system's self-run beats the others'): Mem0 claims 92.5 LOCOMO / 94.4 LongMemEval on its managed platform (OSS parity explicitly not identical); MIRIX 85.4 LOCOMO with gpt-4.1-mini; Zep +18.5% LongMemEval accuracy with 90% latency reduction; all systems agree LOCOMO is small and full-context nearly saturates it.
- **No surveyed system combines** Postgres-only storage, local-first AI, per-type routing, bi-temporal validity, git-keyed code memory, and auto skill generation in one Apache-2.0 engine — that combination is onememory's open lane.

## Findings

### 1. Mem0 (mem0ai/mem0) — the two-phase write pipeline

- **License / maintenance**: Apache-2.0; 66.5k stars, 7.8k forks, 2,667 commits, 416 releases; latest release `ts-v3.3.1` (2026-09-25); last commit 2026-10-01; 412 contributors. https://github.com/mem0ai/mem0
- **TS vs Python**: Python 58.5% / TypeScript 40.4% (monorepo: `mem0/` Python SDK, `mem0-ts/` TS SDK, `server/`, `cli/`, per-agent plugin dirs). https://github.com/mem0ai/mem0
- **Taxonomy**: flat natural-language "memories" scoped to User / Session / Agent; graph variant Mem0ᵍ (entity nodes + relation triplets). https://github.com/mem0ai/mem0
- **Pipeline (paper arXiv:2504.19413)**: two phases. *Extraction*: on each message pair (m₍t−1₎, mₜ), prompt P = (async-refreshed conversation summary S, last m=10 messages, the pair) → LLM extracts candidate facts Ω. *Update*: for each candidate, retrieve top s=10 semantically similar memories via embeddings, then an LLM function-call picks **ADD** (no equivalent) / **UPDATE** (only if the new fact's information content exceeds the old) / **DELETE** (contradicted) / **NOOP** (duplicate or irrelevant). All LLM ops GPT-4o-mini. https://arxiv.org/abs/2504.19413 ; algorithm at https://arxiv.org/html/2504.19413v1 (Appendix B)
- **Mem0ᵍ variant**: Neo4j directed labeled graph; entity nodes carry (type, embedding vector, created timestamp); edges are triplets (vₛ, r, v_d); node match threshold t; on conflicting relations, an LLM update resolver **marks relationships invalid rather than physically deleting** them, enabling temporal reasoning. https://arxiv.org/html/2504.19413v1 (§2.2)
- **Storage**: self-hosted server defaults to **Postgres + pgvector** (bundled providers openai/anthropic/gemini); library defaults to local Qdrant + SQLite history (`~/.mem0/history.db`); default LLM gpt-5-mini, embedder text-embedding-3-small; server features: async memory, metadata filters, reranker search, multimodal, per-user API keys, request audit log, dashboard. https://docs.mem0.ai/open-source/overview
- **Dedup / contradiction / temporal**: LLM-selected ADD/UPDATE/DELETE/NOOP against top-10 similar memories (paper); facts carry timestamps but there is **no bi-temporal model** (silence). The April 2026 rewrite moved to *single-pass ADD-only extraction — one LLM call, no UPDATE/DELETE; memories accumulate, nothing overwritten* — with agent-confirmed actions stored as first-class facts, entity linking across memories, and contradiction/dedup handled at retrieval time. https://github.com/mem0ai/mem0
- **Retrieval**: 2026 algorithm = multi-signal (semantic + BM25 keyword + entity matching) scored in parallel and fused, temporal-aware ranking of dated instances, top-200 retrieval budget, single retrieval call (no agentic loops). https://github.com/mem0ai/mem0
- **LOCOMO methodology**: 10 conversations, ~600 dialogues, ~26k tokens avg, ~200 questions each; four categories (single-hop, multi-hop, temporal, open-domain); the adversarial/unanswerable category **excluded** for lack of ground truth. Metrics: LLM-as-a-Judge over 10 runs (mean ±1 SD) plus F1/BLEU-1; deployment metrics = retrieved-token count (tiktoken cl100k_base), search latency, total latency. https://arxiv.org/html/2504.19413v1 (§3.1–3.2)
- **Headline metrics (paper)**: 26% relative J improvement over OpenAI memory; Mem0ᵍ ≈ +2% over Mem0; **91% lower p95 latency and >90% token savings vs full-context**. Per-category J (gpt-4o-mini): Mem0 single-hop 67.13 / multi-hop 51.15 / temporal 55.51 / open-domain 72.93; Mem0ᵍ temporal 58.13 (best); Zep wins open-domain (76.60); OpenAI scores <15 on temporal (missing timestamps). https://arxiv.org/html/2504.19413v1 (§4.1, abstract)
- **Headline metrics (2026 README)**: LoCoMo 92.5 (old 71.4), LongMemEval 94.4 (old 67.8), BEAM-1M 64.1 / BEAM-10M 48.6. **Stated caveat**: these are managed-platform numbers including proprietary optimizations; OSS users should expect "directionally similar gains but not identical numbers." https://github.com/mem0ai/mem0
- **REST/CLI/agent surfaces**: `mem0 init/add/search` CLI; agent plugins (.claude-plugin, .codex-plugin, .cursor-plugin, .kimi-plugin); reference + pipeline agent skills (`npx skills add …`); agents can mint API keys in <5s with later human claim. https://github.com/mem0ai/mem0
- **OpenMemory MCP (flag)**: OpenMemory was Mem0's earlier local-first deployment model (https://deepwiki.com/mem0ai/mem0/15.1-openmemory-overview-and-migration); a third-party guide reports one of the four mem0 MCP offerings is archived (https://contextbolt.com/blog/mem0-mcp/); the current README no longer mentions OpenMemory at all. Treat as deprecated — verify before citing in an ADR.
- **License boundary**: Apache-2.0 code, but platform-only algorithmic optimizations and hosted features are closed; evaluation moved to a separate repo `mem0ai/memory-benchmarks` (in-repo `evaluation/` retired 2026-06). https://github.com/mem0ai/mem0

### 2. Zep / Graphiti (getzep/graphiti) — bi-temporal knowledge graph

- **License / maintenance**: Graphiti code Apache-2.0; 31.4k stars, 3.2k forks, 998 commits; latest release v0.30.2 (2026-09-08); last commit 2026-09-30. **Note**: the Zep *paper* (arXiv:2501.13956) is CC BY-NC-SA 4.0 — code and paper licenses differ. https://github.com/getzep/graphiti
- **TS vs Python**: Python 99.3% (ships an MCP server and a REST server, but no TS SDK for the core). https://github.com/getzep/graphiti
- **Taxonomy**: three hierarchical subgraphs over G=(N,E,φ): **episode subgraph** (raw messages/text/JSON — a non-lossy store with bidirectional indices linking derived semantic artifacts back to sources), **semantic entity subgraph** (resolved entity nodes + fact edges), **community subgraph** (label-propagation clusters with map-reduce summaries; community names embedded for cosine search). https://arxiv.org/html/2501.13956v1 (§2)
- **Bi-temporal model (the key idea)**: every fact edge carries **valid_at / invalid_at** (when the fact was true in the real world; relative dates resolved against a reference timestamp t_ref) **and created_at / expired_at** (when the system knew it) — timeline T (world) vs T′ (transactions). On new evidence, an LLM compares the new edge to semantically related existing edges; **temporally overlapping contradictions invalidate the old edge** (t_invalid := new edge's t_valid); the transactional timeline consistently prioritizes new information. Nothing is deleted; history is queryable. https://arxiv.org/html/2501.13956v1 (§2.2.3)
- **Entity resolution pipeline**: extraction with last n=4 messages of context + reflexion-style reflection; embed entity name (1024-dim) → cosine + full-text candidates → LLM resolution prompt (is_duplicate, existing uuid, merged full name + summary). Writes use **predefined Cypher, never LLM-generated queries** (consistent schema, less hallucination). https://arxiv.org/html/2501.13956v1 (§2.2.1)
- **Dedup**: edge dedup mirrors entity resolution, but the candidate hybrid search is **constrained to edges between the same entity pair** — prevents cross-entity false merges and cuts the search space. Same fact across different entity pairs is modeled as hyper-edges. https://arxiv.org/html/2501.13956v1 (§2.2.2)
- **Communities**: label propagation (not Leiden) chosen for cheap dynamic extension (new node joins the plurality community of its neighbors); periodic full refresh still required (drift acknowledged). https://arxiv.org/html/2501.13956v1 (§2.3)
- **Retrieval**: hybrid **cosine similarity + Okapi BM25 full-text (Lucene) + n-hop BFS**; BFS can be seeded by recent episodes to pull "recently mentioned" context. Rerankers: RRF, MMR, episode-mentions frequency, node-distance-from-centroid, and cross-encoder (LLM-based, "highest computational cost"). A constructor renders facts **with their valid/invalid date ranges** into the context string. BGE-m3 for embedding + rerank; gpt-4o-mini for graph construction. https://arxiv.org/html/2501.13956v1 (§3, §4.1)
- **Evaluation**: DMR benchmark — Zep 94.8% vs MemGPT 93.4% (gpt-4-turbo), but full-context hits 94.4% (gpt-4-turbo) and 98.0% (gpt-4o-mini); Zep's own paper critiques DMR: single-turn factoids, ambiguous phrasing, tiny scale (~60 messages/conversation). LongMemEval-S (~115k-token conversations; six question types incl. knowledge-update and temporal-reasoning; retrieve top-20 edges + top-20 entity nodes): **+15.2% (gpt-4o-mini) / +18.5% (gpt-4o) accuracy over full-context with ~90% latency reduction**; largest gains on single-session-preference, multi-session, temporal-reasoning; knowledge-update improves only with stronger models — weaker models misread Zep's temporal data. https://arxiv.org/html/2501.13956v1 (§4.2–4.3)
- **Infrastructure**: requires a graph DB — Neo4j (Lucene fulltext), FalkorDB (RedisSearch + vecf32), Kuzu, or Amazon Neptune; MCP server routes tools per `group_id` with per-group graphs; opt-out PostHog telemetry (`GRAPHITI_TELEMETRY_ENABLED=false`); structured-output dependence documented with json_schema vs json_object fallback modes for small/local models. https://github.com/getzep/graphiti

### 3. Letta / MemGPT (letta-ai/letta) — memory blocks + sleep-time compute

- **License / maintenance**: Apache-2.0; 25.0k stars, 2.6k forks, 7,474 commits; last release on the main repo v0.16.8 (2026-05-14). **The legacy V1 Python API server is archived** (README: "retired Letta V1 API server… active projects should use the current source"). https://github.com/letta-ai/letta
- **TS vs Python**: active development moved to `letta-ai/letta-code` — a TypeScript agent harness/terminal UI/App Server distributed via npm (`@letta-ai/letta-code`); the classic Python server is historical. https://github.com/letta-ai/letta
- **Taxonomy**: **core memory blocks** (in-context, always visible), **recall memory** (conversation history), **archival memory** (out-of-context store for saved memories). https://www.letta.com/blog/sleep-time-compute
- **Memory blocks & injection**: a block = {label, description, value, limit(chars)}; blocks are prepended to the system prompt in an XML-like `<memory_blocks>` envelope with per-block `chars_current`/`chars_limit` metadata; `persona` and `human` are default labels with autogenerated descriptions; blocks can be read-only and **shared across multiple agents** (update once, visible everywhere); agents edit blocks via built-in memory tools. https://docs.letta.com/guides/agents/memory-blocks
- **Persistence model**: all state — memories, user messages, reasoning, tool calls — is persisted in a database and survives context eviction; core memories are injected into context; the agent self-edits memory through tools. https://docs.letta.com/v1-sdk/concepts/stateful-aggers (engine not named in current docs — silence, verify if it matters for us)
- **Sleep-time compute (arXiv:2504.13171)**: a "sleep-time enabled agent" is **two agents**: a primary (talks to users, calls tools, searches recall/archival) **without core-memory edit tools**, and a sleep-time agent that **owns the memory-editing tools for the primary's in-context memory** plus its own. Memory management becomes asynchronous; sleep-time continuously turns "raw context" into "learned context"; the pair can use different models (fast primary, stronger model at night); runs on a configurable frequency or on context compaction; memory stays readable "anytime" while consolidation proceeds. Claimed Pareto improvement (latency shifted to idle time) on AIME/GSM. https://www.letta.com/blog/sleep-time-compute
- **Letta Code today (most relevant to onememory)**: memory is **MemFS — a git-backed memory filesystem** the agent inspects and edits; `/init` bootstraps project memory (asks about working style, reviews prior sessions via subagents); `/remember <lesson>` teaches explicitly and commits to MemFS; **`/doctor` audits memory placement, duplication, and system-prompt token usage**; "dreaming" = background subagents reviewing recent conversations and consolidating lessons (after N steps or on compaction; optional "agent reviews before applying" second pass); a reorganize workflow backs up the repo before splitting large files / merging duplicates. https://docs.letta.com/letta-agent/memory ; git-based context repositories: https://www.letta.com/blog/context-repositories
- **Evaluation**: MemGPT's DMR 93.4% (gpt-4-turbo, as reported by Zep's paper); the Zep team could not run Letta on LongMemEval at all (no direct history-ingestion path; archival workaround failed) — a notable integration gap. https://arxiv.org/html/2501.13956v1 (§4.3.1)

### 4. MIRIX (Mirix-AI/MIRIX) — closest published taxonomy to ours

- **License / maintenance**: Apache-2.0; 3.5k stars, 274 forks, 383 commits, last commit 2026-08-20; built on Letta (acknowledged in README). **Flag**: parent brief said `mirix-research/MIRIX` — that URL 404s; current home is https://github.com/Mirix-AI/MIRIX . Paper arXiv:2507.07957 is CC BY 4.0. https://arxiv.org/abs/2507.07957
- **TS vs Python**: Python 96.3% (React-Electron frontend + Uvicorn backend per the paper). https://arxiv.org/html/2507.07957v1 (§2.1)
- **Taxonomy (six types with concrete schemas)** — https://arxiv.org/html/2507.07957v1 (§3.1):
  - **Core**: persona + human blocks (MemGPT-inspired); when memory exceeds 90% of capacity, a controlled rewrite compacts without losing critical information.
  - **Episodic**: {event_type: user_message | inferred_result | system_notification, summary, details, actor: user | assistant, timestamp} — a structured, temporally indexable log/calendar.
  - **Semantic**: {name, summary, details, source: user_provided | Wikipedia | inferred} — time-independent concepts/entities/relations; visualized as a tree.
  - **Procedural**: {entry_type: workflow | guide | script, goal description, steps (optionally JSON)} — actionable how-to knowledge.
  - **Resource**: {title, summary, resource_type: doc | markdown | pdf_text | image | voice_transcript, full-or-excerpted content} — documents/media the user is actively engaged with.
  - **Knowledge Vault**: {entry_type: credential | bookmark | contact_info | api_key, source, **sensitivity: low|medium|high**, secret_value} — verbatim/sensitive facts; high-sensitivity entries access-controlled and **excluded from casual retrieval**.
- **Routing & multi-agent design**: 8 agents — a Meta Memory Manager routes each input (post an initial memory search) to six per-type Memory Managers, plus a Chat Agent. https://arxiv.org/html/2507.07957v1 (§3.3)
- **Retrieval — Active Retrieval**: before answering, the agent generates a *topic* from the input, retrieves **top-10 entries from each of the six components**, and injects them into the system prompt wrapped in typed tags (`<episodic_memory>…</episodic_memory>`) so the model knows content and origin. Retrieval functions: `embedding_match`, `bm25_match`, `string_match` (more planned). https://arxiv.org/html/2507.07957v1 (§3.2)
- **Evaluation**: ScreenshotVQA (5k–20k hi-res screenshots per sequence): **+35% over RAG with 99.9% storage reduction; +410% over long-context with 93.3% storage reduction**. LOCOMO: **85.38% overall** (gpt-4.1-mini; three runs 83.98/87.34/84.82), "outperforming the best existing method by 8.0%". Baseline table (gpt-4o-mini): A-Mem 48.38, LangMem 58.10, OpenAI 52.90, Mem0 66.88, Mem0ᵍ 68.44, Memobase 70.91, Zep 75.14, Full-Context 77.51. https://arxiv.org/html/2507.07957v1 (§1, Appendix A)
- **Conflict flagged by the authors**: with gpt-4.1-mini via mem0's harness, Zep scored only 49.09 overall — "we are afraid there might be errors in their implementation," so it was omitted. Cross-vendor benchmark harnesses are not comparable. https://arxiv.org/html/2507.07957v1 (Appendix A)
- **Storage**: Docker images for Postgres, Redis, backend API; packaged app stores memory locally for privacy; per-client scope filters (`filter_tags`/scopes) enforced on reads across all five document managers. https://github.com/Mirix-AI/MIRIX
- **Post-paper evolution (repo)**: per-session `session_tag` routing ("task" → procedural skill distillation only; "conversation" → episodic/semantic extraction); `POST /memory/auto_dream` consolidation endpoint with per-component modes (core/episodic/semantic/resource/procedural/knowledge/experience) and `dry_run`; procedural skills distilled from sessions **including tool calls, errors, retries, and the fix that worked**; ALFWorld SkillOpt 68.7% vs 52.2% no-skill baseline; LOCOMO-10 81.23% on gpt-5.2. https://github.com/Mirix-AI/MIRIX

### 5. Memp — procedural memory evolution

- **Paper**: arXiv:2508.06433 (v4 2026-04-15), ACL 2026 Findings. **Flag**: parent brief said `bytedance/Memp`; the paper links code at `github.com/zjunlp/MemP` (Zhejiang NLP group; ByteDance researchers co-author). https://arxiv.org/abs/2508.06433
- **Taxonomy**: procedural memory only — distilled from past agent trajectories into **fine-grained step-by-step instructions AND higher-level script-like abstractions** (two granularities). https://arxiv.org/abs/2508.06433
- **Pipeline**: explicitly studies three strategy axes — **Build / Retrieval / Update** — coupled with a "dynamic regimen" that continuously **updates, corrects, and deprecates** repository contents so it evolves in lockstep with new experience. https://arxiv.org/abs/2508.06433
- **Dedup/temporal**: deprecation and correction are first-class (outdated procedures retired, wrong ones fixed); no bi-temporal claims (silence).
- **Evaluation**: TravelPlanner + ALFWorld — as the repository is refined, agents achieve steadily higher success and efficiency on analogous tasks; **procedural memory built by a stronger model retains value when migrated to a weaker model (substantial gains)**. https://arxiv.org/abs/2508.06433
- **Relevance**: the strongest published foundation for our procedural + failure layers and auto skill generation: two granularities, explicit deprecation, model-agnostic transfer.

### 6. MemOS / MemCube (MemTensor/MemOS) — memory-as-OS lifecycle vocabulary

- **License / maintenance**: Apache-2.0; 11.7k stars, 1.1k forks, 2,177 commits; latest v2.0.34 (2026-09-23); last commit 2026-09-22. Paper arXiv:2507.03724 (v4 2025-12-03, CC BY 4.0). https://github.com/MemTensor/MemOS
- **TS vs Python**: TypeScript 58.7% / Python 34.2% — the local coding-agent plugin is TypeScript; the core/service is Python. https://github.com/MemTensor/MemOS
- **Taxonomy**: a **MemCube** is the universal memory unit — content + metadata (**provenance, versioning**) — unifying three substrates: **plaintext memory, activation memory (KV-cache), parameter memory**; MemCubes can be **composed, migrated, and fused** (retrieval ↔ parameter-based learning). https://arxiv.org/abs/2507.03724 (abstract)
- **Lifecycle & components**: memory lifecycle = **generation, activation, fusion, archiving, expiration**, orchestrated by MemReader, **MemScheduler**, MemLifecycle, MemOperator, behind a unified Memory API with multi-level permission control and operation auditing; a layered hierarchy of **working memory / long-term storage / cold archives governed by recency, access frequency, importance**; explicitly attacks "memory islands" (ChatGPT memory can't follow you into Cursor). https://arxiv.org/html/2507.03724v4 (§1)
- **Plaintext memory specifics**: integrated into the inference loop; **high-frequency plaintext can be promoted into activation paths** (externalization/internalization); stored in a **hierarchical graph organized by task–concept–fact paths**; task parsing + semantic similarity + topic-aware routing for prioritized retrieval; **conflict detection, deduplication, versioning, and forgetting policies**. MemCube organizes semantic fragments multi-dimensionally, enabling query-based aggregation and multi-granularity activation. https://arxiv.org/html/2507.03724v4 (§2)
- **Evaluation**: MemOS-1031 reported first on PreFEval, PersonaMem, LongMemEval, and LoCoMo vs MIRIX, Mem0, Zep, Memobase, MemU, Supermemory (self-reported figure; full tables in paper Tables 3–6). https://arxiv.org/html/2507.03724v4 (Fig. 1)
- **Shipped product (repo)**: local plugin is TypeScript, **100% on-device, local-first SQLite**, hybrid retrieval **FTS5 + vector**, "smart dedup", **tiered skill evolution: L1 traces / L2 policies / L3 world model**, multi-agent collaboration; cloud + local plugins for OpenClaw, Hermes Agent, DeepSeek Harness; headline claim "35.24% token savings"; server deployment ships Neo4j + Qdrant via Helm. https://github.com/MemTensor/MemOS
- **Adopt the vocabulary, not the architecture**: activation/KV/parameter cubes require model-internal access (KV injection, steering vectors) that an agent-side engine doesn't have.

### 7. A-Mem (agiresearch/A-mem) — Zettelkasten dynamic linking

- **License / maintenance**: **MIT**; 1.2k stars, 123 forks, 31 commits, no releases, last commit 2025-12-12 (effectively dormant); evaluation code lives in a separate repo `WujiangXu/AgenticMemory`. Paper arXiv:2502.12110 (v11 2025-10-08), NeurIPS 2025. https://github.com/agiresearch/A-mem ; https://arxiv.org/abs/2502.12110
- **TS vs Python**: Python 100%. https://github.com/agiresearch/A-mem
- **Taxonomy**: notes (Zettelkasten): each memory becomes a note with structured attributes — **contextual description, keywords, tags**, timestamp. https://arxiv.org/abs/2502.12110
- **Pipeline**: on insert, embed the note and retrieve related historical notes via ChromaDB → an LLM establishes **links** based on similarity/shared attributes → **memory evolution**: new memories trigger updates to existing notes' contextual representations and attributes, so the network continuously refines. https://arxiv.org/abs/2502.12110 ; https://github.com/agiresearch/A-mem
- **Storage / retrieval**: ChromaDB vector store; API `add_note/read/search_agentic/update/delete`; OpenAI or Ollama backends. https://github.com/agiresearch/A-mem
- **Dedup/temporal**: link/merge-based; timestamps only; **no validity/invalidity model** (silence).
- **Evaluation**: "six foundation models," superior vs SOTA baselines (paper abstract). Third-party reruns are much less flattering: Mem0 reports A-Mem lags by >25 J points (https://arxiv.org/html/2504.19413v1 §4.1); MIRIX's table has A-Mem at 48.38 overall (gpt-4o-mini) (https://arxiv.org/html/2507.07957v1 Appendix A).
- **Take**: treat as a paper artifact, not infra to depend on.

### 8. cognee (topoteretes/cognee) — KG pipeline, Postgres full-stack

- **License / maintenance**: Apache-2.0; 31.3k stars, 3.2k forks, 10,984 commits; latest v1.6.2 (2026-09-29); last commit 2026-10-01; 307 contributors. https://github.com/topoteretes/cognee
- **TS vs Python**: Python 86.7% / TypeScript 11.7% (frontend + some tooling). https://github.com/topoteretes/cognee
- **Pipeline**: `cognee.remember(...)` / `add` → **`cognify()`** (chunking → entity/edge extraction → ontology grounding → community summarization) → hybrid search; deletion via `datasets.delete_data`; edits reconcile graph state. The brand name for this pipeline is ECL (Extract–Cognify–Load) — **flag**: the fetched README sections did not surface the acronym (page truncation); verify on docs.cognee.com before citing in an ADR. https://github.com/topoteretes/cognee
- **Ontology grounding (opt-in)**: default `annotate` canonicalizes/enriches matched entities (byte-identical default pipeline); `ONTOLOGY_MODE=strict` drops extracted entities with neither a class match on type nor an individual match on name, and filters edges touching dropped nodes (chunk text stays stored/embedded). https://github.com/topoteretes/cognee (PR #4848)
- **Storage — key data point**: "Since cognee 1.0 you can run the entire memory layer on a single Postgres instance" — relational metadata + PGVector + graph state in one Postgres service. **OSS boundary flag**: shipped as a *demo feature*; "the production-ready version is available as a licensed product." Other backends: LanceDB/SQLite/Kuzu/Neo4j in tests and CI. https://github.com/topoteretes/cognee
- **Local-first AI**: v1.6.0 (2026-09-18) added keyless workflows — build and search text memory with local models and no cloud LLM key; LLM-dependent improvement stages skip when no LLM is configured; pipeline recovery preserves completed documents after crashes. https://github.com/topoteretes/cognee/releases/tag/v1.6.0
- **Code memory**: an in-repo codegraph pipeline exists (source-code chunking, code summarization, SWE-bench retrieval experiments). https://github.com/topoteretes/cognee (commit history)
- **Retrieval**: multiple search types incl. graph completion, RAG completion, hybrid graph+lexical; `external_metadata` stamped on chunks and surfaced in hybrid retrieval (v1.6.1). https://github.com/topoteretes/cognee
- **Evaluation**: BEAM framework in-repo: **0.79 @ 100K-token context, 0.67 @ 10M**, with explicit caveats ("Read the methodology… before comparing these scores with other systems"). Research backing: arXiv:2505.24478 "Optimizing the Interface Between Knowledge Graphs and LLMs for Complex Reasoning." MCP server ships as `cognee-mcp`. https://github.com/topoteretes/cognee ; https://arxiv.org/abs/2505.24478

### 9. Skim: MemAgent (RL-based memory management)

- MemAgent (arXiv:2507.02259, ICLR 2026 Oral; Tsinghua AIR + ByteDance Seed) trains an agent with RL (extended DAPO; independent-context multi-conversation generation) to **read text in segments and overwrite a fixed-length memory after each segment**: an 8K-context model trained on 32K text extrapolates to a **3.5M-token QA task with <5% performance loss, and 95%+ on 512K RULER**. https://arxiv.org/abs/2507.02259 ; https://memagent-sialab.github.io/
- Takeaway: a learned fixed-size overwrite memory can rival full-context — but it requires a *trained model*, not tool-called infrastructure. Not directly implementable in onememory; still an argument for strict retrieval budgets.

### 10. Skim: memU (NevaMind-AI/memU) — agent-authored wiki + host adapters

- memU (Apache-2.0; 14.5k stars, 1.1k forks, 458 commits; latest release v1.5.1, 2026-03-23; Python 99.6%) stores memory as an **agent-editable wiki** across sessions/agents/devices, with core memory logic "only 500 lines." https://github.com/NevaMind-AI/memU
- Host adapters ship one binary per coding agent (Codex, Claude Code, Cursor, OpenClaw, Hermes, WorkBuddy, Cola, pi), each mining that agent's **session logs** (JSONL/SQLite, read-only) and patching its **instruction file** (AGENTS.md / CLAUDE.md / SOUL.md / MEMORY.md) — two seams: "record" and "inject"; `memu-agent detect` sniffs unknown hosts' JSONL dialects. https://github.com/NevaMind-AI/memU
- **Automatic skill extraction**: a scheduled task slices new sessions into self-contained jobs; *the agent itself* decides to do nothing / patch an existing skill / create a new one, and writes readable Markdown (name, description, reusable workflow, edge cases, pitfalls); `commit` embeds name+description and stores under the "skill" track; retrieved on similar future tasks. **MemoryService makes no LLM or chat calls** — judgment stays in the agent. https://github.com/NevaMind-AI/memU
- Storage: in-memory / SQLite (brute-force cosine) / **Postgres + pgvector**; local or cloud backend via `MEMU_MEMORY_MODE`. https://github.com/NevaMind-AI/memU

## What onememory should adopt

Mapped to our lifecycle (observe→ingest→normalize→extract→classify→dedupe→entity-resolve→score→store→retrieve→reinforce→consolidate→decay→archive) and our ten layers.

1. **Bi-temporal columns on every memory row** (Zep): `valid_at`/`invalid_at` (fact truth in the world) + `created_at`/`expired_at` (system knowledge). Contradiction ⇒ **invalidate, never delete** (Zep edge invalidation; Mem0ᵍ marks relations invalid for the same reason). Feeds store, reinforce, decay, archive. https://arxiv.org/html/2501.13956v1 (§2.2.3)
2. **Two-phase extract-then-resolve write loop** (Mem0 paper): candidate facts → compare against top-s semantically similar memories → explicit ADD/UPDATE/DELETE/NOOP decision; UPDATE only when new information content exceeds the old (Algorithm 1). But run it **off the hot path**: Mem0's 2026 production algorithm went single-pass ADD-only, and Letta/MIRIX both push memory mutation to background agents (sleep-time; auto-dream; MIRIX's ~60s screenshot batch cadence). Recommended shape: cheap classify+dedupe at write; contradiction resolution deferred to consolidate. https://arxiv.org/html/2504.19413v1 ; https://www.letta.com/blog/sleep-time-compute
3. **Per-type schemas from MIRIX** as the schema baseline across our ten layers: episodic = {event_type, summary, details, actor, timestamp}; semantic = {name, summary, details, source}; procedural = {entry_type, goal, steps}; working ≈ MIRIX core (capacity % + controlled rewrite at 90%); source ≈ MIRIX resource ({title, summary, resource_type, content}); preference ≈ sensitivity-tagged semantic/core hybrid. https://arxiv.org/html/2507.07957v1 (§3.1)
4. **Active Retrieval with per-type routing** (MIRIX): auto-generate a topic per turn, retrieve top-k **per layer**, inject with typed tags and (Zep) validity date ranges; budget-aware (Zep retrieves top-20 edges + 20 nodes; Mem0 uses a top-200 budget). This is the retrieval half of our token-budgeted hybrid design. https://arxiv.org/html/2507.07957v1 (§3.2) ; https://arxiv.org/html/2501.13956v1 (§4)
5. **Hybrid multi-signal retrieval + fused ranking** (Mem0 2026, Zep, MIRIX): semantic (pgvector) + BM25/FTS + entity-match signals scored in parallel and fused; optional graph expansion (Zep BFS seeded by recent episodes); optional cross-encoder rerank behind a cost flag (Zep calls it the most expensive reranker). https://github.com/mem0ai/mem0 ; https://arxiv.org/html/2501.13956v1 (§3.2)
6. **Entity resolution as its own lifecycle stage** (Zep): cosine + full-text candidates → LLM resolves duplicates with merged name/summary; **constrain fact dedup to the same entity pair** to prevent cross-entity false merges; entity linking then boosts retrieval (Mem0 2026). Feeds our dedupe + entity-resolve stages. https://arxiv.org/html/2501.13956v1 (§2.2)
7. **Sleep-time consolidation as an engine primitive** (Letta + MIRIX): a background job owns memory mutation (the primary agent never edits on the hot path); configurable frequency or on-compaction trigger; per-component modes with `dry_run` (MIRIX auto-dream); review-before-apply option (Letta dreaming); stronger-model-at-night split (Letta). Feeds reinforce/consolidate/decay. https://www.letta.com/blog/sleep-time-compute ; https://github.com/Mirix-AI/MIRIX
8. **Procedural/failure layers with two granularities + deprecation** (Memp + MIRIX + memU + MemOS): distill trajectories into step-level and script-level skills; mine **tool errors, retries, and the fix that worked** as first-class failure-layer signals (MIRIX skill distillation; ALFWorld 68.7% vs 52.2%); agent-authored Markdown skills committed, embedded, retrieved (memU); tiered evolution L1 traces → L2 policies → L3 world model (MemOS local plugin); explicit correction/deprecation lifecycle (Memp). This is the published basis for our procedural, failure, and auto-skill-generation features. https://arxiv.org/abs/2508.06433 ; https://github.com/NevaMind-AI/memU ; https://github.com/MemTensor/MemOS
9. **Git-keyed code/project memory** (Letta MemFS + memU): memory as inspectable, git-versioned files; `/init` bootstrap, explicit `/remember` teach, **`/doctor` audit of placement/duplication/token usage** as UX verbs; memU's two integration seams (mine session logs = record; patch AGENTS.md/CLAUDE.md = inject) define exactly how a sidecar engine attaches to Claude Code/Codex/Cursor/pi without agent-binary cooperation. Validates our git-fingerprint project layer. https://docs.letta.com/letta-agent/memory ; https://github.com/NevaMind-AI/memU
10. **Postgres + pgvector single store** (Mem0 self-hosted + cognee + memU): all three ship Postgres+pgvector on the self-hosted path; cognee even runs relational + vector + graph state in one Postgres (with a demo-vs-licensed split we should not replicate). Supports our Docker-Postgres default and the PGlite embedded evaluation; avoids Zep's mandatory Neo4j/FalkorDB. https://docs.mem0.ai/open-source/overview ; https://github.com/topoteretes/cognee
11. **MemOS lifecycle vocabulary for decay/archive**: explicit states (active/archived/expired) + provenance + versioning on every row; hot/warm/cold promotion governed by recency, access frequency, and importance (MemOS working/long-term/cold archives); MemoryBank's strengthen-on-recall/decay-when-unused pattern is described in Mem0's paper appendix. https://arxiv.org/html/2507.03724v4 (§1) ; https://arxiv.org/html/2504.19413v1 (Appendix C)
12. **Ops surface**: CLI (`mem0 init/add/search`); MCP server with per-group/user scoping (Graphiti); self-hosted REST with per-user API keys + request audit log + async memory + metadata filters (Mem0 OSS server); per-client read/write scope filters on every memory table (MIRIX `filter_tags`/scope enforcement). https://github.com/mem0ai/mem0 ; https://github.com/getzep/graphiti ; https://docs.mem0.ai/open-source/overview ; https://github.com/Mirix-AI/MIRIX
13. **Evaluation discipline** (Mem0's dual metrics): always report per-question-type LLM-as-Judge **plus** deployment metrics (retrieved tokens, p95 search/total latency) over ≥10 runs; LOCOMO + LongMemEval primary, BEAM for 100K–10M scale (cognee); publish a reproducible OSS harness (Mem0 open-sourced `memory-benchmarks` for exactly this reason). https://arxiv.org/html/2504.19413v1 (§3.2) ; https://github.com/topoteretes/cognee

## What to avoid

1. **DMR as a headline benchmark** — Zep's own paper dissects it: single-turn factoids, ambiguous phrasing, ~60 messages/conversation, and full-context nearly ties the best memory system. https://arxiv.org/html/2501.13956v1 (§4.2)
2. **LOCOMO-only SOTA claims** — at ~9k tokens/conversation, full-context is nearly the upper bound (MIRIX: full-context 77.51 on gpt-4o-mini and 88.13 on gpt-4.1-mini, beating every memory system). Cross-vendor harnesses also disagree wildly (Zep = 75.14 in MIRIX's gpt-4o-mini run vs 49.09 via the mem0 harness on gpt-4.1-mini — flagged by MIRIX as a probable harness bug). https://arxiv.org/html/2507.07957v1
3. **Inline LLM UPDATE/DELETE in the hot path** — Mem0's production algorithm dropped UPDATE/DELETE for single-pass ADD-only; Zep and Mem0ᵍ avoid destructive deletes entirely; a wrong DELETE destroys history irrecoverably. https://github.com/mem0ai/mem0
4. **A hard graph-database dependency** — Graphiti requires Neo4j/FalkorDB/Kuzu/Neptune: a heavy install for a local-first coding tool; Mem0's 2026 pivot (entity linking + hybrid retrieval, graph deprioritized) and cognee's Postgres-graph demo suggest a relational projection suffices at our scale. https://github.com/getzep/graphiti
5. **One flat memory store** — MIRIX's opening critique of Letta/Mem0/ChatGPT: no compositional structure, no per-type routing, poor multi-modal support. We have ten layers; keep retrieval per-type. https://arxiv.org/html/2507.07957v1 (§1)
6. **A standing LLM-in-the-engine call per ingest** — memU's design principle ("MemoryService makes no LLM calls"; judgment stays in the agent), plus Mem0's async summary module and MIRIX's batching (~20 screenshots / ~60s), all point the same way: batch, background, or delegate. https://github.com/NevaMind-AI/memU
7. **Eight separate agents to manage memory** (MIRIX) — too heavy for a self-hosted CLI product; implement per-type managers as prompt stages/policies inside one engine, not independent agents.
8. **Storing raw secrets by default** (MIRIX Knowledge Vault keeps api_key/credential values) — for a coding-agent memory engine this is a liability; prefer detect-and-redact with a pointer to the OS keychain, or an explicit off-by-default vault. https://arxiv.org/html/2507.07957v1 (§3.1)
9. **Default-on telemetry** — Graphiti ships opt-out PostHog analytics; for a local-first, privacy-positioned product, telemetry must be opt-in. https://github.com/getzep/graphiti
10. **Licensed "production" splits of core functionality** — cognee's Postgres graph store is a demo in Apache-2.0 with the production version licensed; Mem0's best benchmark numbers are platform-only. onememory's differentiator is the whole loop at full fidelity under Apache-2.0. https://github.com/topoteretes/cognee ; https://github.com/mem0ai/mem0
11. **Activation/KV/parameter memory cubes** (MemOS) — they require model-internal access (KV injection, steering vectors); borrow the lifecycle/provenance/versioning vocabulary only. https://arxiv.org/html/2507.03724v4
12. **Learned-overwrite memory** (MemAgent) — requires an RL-trained model; incompatible with a provider-agnostic, tool-called memory engine. https://arxiv.org/abs/2507.02259

## Open questions

1. **OpenMemory MCP status** — third-party sources describe it as Mem0's earlier local-first deployment (DeepWiki; ContextBolt reports one mem0 MCP archived); the current README is silent. Verify directly before writing our MCP server ADR. https://contextbolt.com/blog/mem0-mcp/
2. **Mem0 OSS-vs-platform parity** — 92.5 LOCOMO / 94.4 LongMemEval are managed-platform numbers ("proprietary optimizations not available in the open-source SDK"); how much of the 2026 algorithm ships in Apache-2.0 `mem0` is unstated. https://github.com/mem0ai/mem0
3. **Letta's current storage engine** — current docs say state is "persisted in a database" and memory files are git-backed (MemFS), but never name the DB engine; the legacy Postgres server is archived. Verify before treating Letta as a storage-schema reference. https://docs.letta.com/letta-agent/memory
4. **Memp code home** — paper links `github.com/zjunlp/MemP`; parent brief said `bytedance/Memp`. Verify the org before citing. https://arxiv.org/abs/2508.06433
5. **cognee ECL naming** — "Extract–Cognify–Load" did not surface in the fetched README sections (truncation); confirm the canonical pipeline name/structure on docs.cognee.com. https://github.com/topoteretes/cognee
6. **Graph projection vs pure relational** — do we need graph edges at all, or do Postgres entity/relation tables + recursive CTEs + pgvector cover our retrieval? Evidence: Zep needs Cypher; Mem0 moved to entity-linking + hybrid fusion without a graph-first store; cognee proves graph state can live in Postgres. Needs a spike.
7. **Secrets policy for preference/source layers** — MIRIX stores secrets with sensitivity tiers; should we redact-and-point instead? Decision needed before schema freeze. https://arxiv.org/html/2507.07957v1 (§3.1)
8. **Unanswerable-question handling** — Mem0 excluded LOCOMO's adversarial category for lack of ground truth; our failure layer could own "recognize unanswerable" as a scored behavior. Design an eval for it. https://arxiv.org/html/2504.19413v1 (§3.1)
9. **BEAM reproduction** — cognee publishes BEAM (0.79 @100K / 0.67 @10M) with a methodology report; Mem0 reports BEAM-1M/10M too. Adopting BEAM for our scale claims requires reproducing their harness. https://github.com/topoteretes/cognee
10. **Cross-model skill transfer** — Memp shows procedural memory built by a stronger model transfers to weaker models; our auto-generated skills should be validated model-agnostic (prose, not model-specific tokens). https://arxiv.org/abs/2508.06433
11. **License asymmetry** — Zep's *paper* is CC BY-NC-SA (code Apache-2.0); A-Mem is MIT; the rest Apache-2.0. If we quote paper text/figures in our docs, respect the paper licenses. https://arxiv.org/abs/2501.13956
12. **Benchmark conflict adjudication** — every system's self-reported LOCOMO/LongMemEval run beats every other system (Mem0 92.5 > MemOS > MIRIX 85.4 > Zep 75.1 > Mem0-paper 66.9, all "LOCOMO overall" with different judges/models/harnesses). Any onememory number must state judge model, harness, and retrieval budget, or it is noise. https://arxiv.org/html/2507.07957v1 (Appendix A)
