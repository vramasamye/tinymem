# Memory-Systems Landscape Research (input to onememory ADRs + schema design)

Date: 2026-10-03. Method: primary sources only — arXiv papers, GitHub repos/READMEs, official docs. All claims carry a source URL; conflicts and silences are flagged inline.

## Summary

The 2025–2026 open-source agent-memory landscape converged on a shared shape: **typed memory layers + an explicit write pipeline (extract → resolve/dedupe → store) + hybrid retrieval + background consolidation**. Mem0 defined the write-time ADD/UPDATE/DELETE/NONE loop (and then, in production, largely abandoned UPDATE/DELETE in favor of single-pass ADD-only plus retrieval-time fusion). Zep/Graphiti defined bi-temporal validity (fact-truth vs system-knowledge timelines) and contradiction-as-invalidation-not-deletion. Letta/MemGPT defined in-context memory blocks plus a background "sleep-time" agent that owns memory edits; its current coding agent stores memory as a git-backed filesystem. MIRIX published the closest taxonomy to ours (six typed memory components with concrete per-type schemas) and a per-type retrieval router. Memp proved procedural memory distills into two granularities (steps + scripts) with explicit correction/deprecation. MemOS contributed the lifecycle vocabulary (generation/activation/fusion/archive/expire, provenance, versioning, permissions) but its activation/KV/parameter cubes are out of scope for an agent-side engine. Storage is consolidating on **Postgres + pgvector** (Mem0 self-hosted server default; cognee full-stack Postgres; memU Postgres option) — strong validation for onememory's Postgres-first bet. Headline metrics: Mem0 claims 92.5 LOCOMO / 94.4 LongMemEval on its managed platform (OSS parity explicitly not identical); MIRIX 85.4 LOCOMO with gpt-4.1-mini; Zep +18.5% LongMemEval accuracy over full-context with 90% latency reduction; all systems agree LOCOMO is small and full-context nearly saturates it. No system combines: Postgres-only, local-first AI, per-type routing, bi-temporal validity, git-keyed code memory, and skill generation — that combination is onememory's open lane.

## Findings

### 1. Mem0 (mem0ai/mem0) — the two-phase write pipeline

- **Repo/license/activity**: Apache-2.0; 66.5k stars, 7.8k forks, 2,667 commits, 416 releases, latest `ts-v3.3.1` (2026-09-25); Python 58.5% / TypeScript 40.4%. https://github.com/mem0ai/mem0
- **Taxonomy**: flat "memories" (natural-language facts) per user/session/agent, plus a graph variant Mem0ᵍ (entities + relation triplets); multi-level memory: User / Session / Agent state (README). https://github.com/mem0ai/mem0
- **Pipeline (paper arXiv:2504.19413)**: two phases. *Extraction*: on each message pair (m₍t−1₎, mₜ), prompt P = (conversation summary S from DB, last m=10 messages, the pair) → LLM extracts candidate facts Ω. Summary refresh runs asynchronously. *Update*: for each candidate, retrieve top s=10 semantically similar memories via embeddings, then an LLM function-call picks **ADD** (no equivalent exists) / **UPDATE** (only if new fact's information content > existing) / **DELETE** (contradicted) / **NOOP** (duplicate/irrelevant). https://arxiv.org/abs/2504.19413 ; algorithm: https://arxiv.org/html/2504.19413v1 (Appendix B)
- **Mem0ᵍ**: Neo4j directed labeled graph; entity nodes carry (type, embedding, created timestamp); edges are triplets (vₛ, r, v_d); node matching threshold t; conflict detection marks obsolete relationships **invalid instead of physically deleting** them, to enable temporal reasoning; dual retrieval = entity-centric (anchor on query entities, expand in/out edges into a subgraph) + semantic triplet (query embedding vs triplet-embedding similarity, threshold, ranked). All LLM ops GPT-4o-mini. https://arxiv.org/html/2504.19413v1 (§2.2)
- **Temporal handling**: timestamps stored with facts; no bi-temporal model (silence in paper); contradiction resolved as DELETE (paper §2.1) or mark-invalid (Mem0ᵍ).
- **LOCOMO methodology**: 10 conversations, ~600 dialogues, ~26k tokens avg, ~200 questions each; four categories (single-hop, multi-hop, temporal, open-domain); adversarial category **excluded** (no ground truth). Metrics: LLM-as-a-Judge over 10 runs (mean ±1 SD) plus F1/BLEU-1; deployment metrics = retrieved-token count (tiktoken cl100k_base), search latency, total latency. https://arxiv.org/html/2504.19413v1 (§3.1–3.2)
- **Headline metrics**: 26% relative J improvement over OpenAI memory; Mem0ᵍ ≈ +2% over Mem0; **91% lower p95 latency and >90% token savings vs full-context** (abstract). Per-category J (gpt-4o-mini): Mem0 single-hop 67.13, multi-hop 51.15, temporal 55.51, open-domain 72.93; Mem0ᵍ temporal 58.13 (best); Zep wins open-domain (76.60); OpenAI <15 on temporal (missing timestamps). https://arxiv.org/html/2504.19413v1 (§4.1)
- **April 2026 algorithm rewrite** (README): *single-pass ADD-only extraction — one LLM call, no UPDATE/DELETE; memories accumulate, nothing overwritten*; agent-generated facts (confirmed actions) are first-class; entity linking across memories; multi-signal retrieval (semantic + BM25 + entity matching scored in parallel and fused); temporal-aware retrieval ranking. Reported: LoCoMo 92.5 (old 71.4), LongMemEval 94.4 (old 67.8), BEAM-1M 64.1 / BEAM-10M 48.6, top-200 retrieval budget, single retrieval call. **Caveat stated by Mem0**: these are managed-platform numbers including proprietary optimizations; OSS users get "directionally similar gains but not identical numbers". https://github.com/mem0ai/mem0
- **OSS/REST/API design**: library (`pip install mem0ai` / `npm install mem0ai`) vs **self-hosted server**: `make bootstrap` / docker compose; dashboard, per-user API keys, request audit log; self-hosted default vector store = **Postgres + pgvector**; library default = local Qdrant + SQLite history (`~/.mem0/history.db`); default LLM gpt-5-mini, embedder text-embedding-3-small; features: async memory, metadata filters, reranker search, multimodal. https://docs.mem0.ai/open-source/overview
- **CLI + agent surfaces**: `mem0 init/add/search`; agent plugins (.claude-plugin, .codex-plugin, .cursor-plugin, .kimi-plugin), agent skills (reference + pipeline), agents can mint their own API keys with later human claim. https://github.com/mem0ai/mem0
- **OpenMemory MCP (flag)**: OpenMemory was Mem0's earlier local-first deployment model (https://deepwiki.com/mem0ai/mem0/15.1-openmemory-overview-and-migration); third-party reports say one of the four mem0 MCP offerings is archived (https://contextbolt.com/blog/mem0-mcp/); the current README no longer mentions OpenMemory at all, steering to plugins/CLI/self-hosted server. Treat OpenMemory as deprecated — verify before citing in an ADR.
- **License boundary**: Apache-2.0 code, but platform-only algorithmic optimizations and hosted features are closed; evaluation moved to a separate repo mem0ai/memory-benchmarks (in-repo evaluation/ retired 2026-06). https://github.com/mem0ai/mem0

### 2. Zep / Graphiti (getzep/graphiti) — bi-temporal knowledge graph

- **Repo/license/activity**: Graphiti code Apache-2.0; 31.4k stars, 3.2k forks, 998 commits, latest v0.30.2 (2026-09-08); Python 99.3%. https://github.com/getzep/graphiti — Note: the Zep **paper** (arXiv:2501.13956) is CC BY-NC-SA 4.0 (https://arxiv.org/abs/2501.13956); code and paper licenses differ.
- **Taxonomy**: three hierarchical subgraphs over G=(N,E,φ): **episode subgraph** (raw messages/text/JSON — non-lossy store, bidirectional indices to derived semantic artifacts), **semantic entity subgraph** (resolved entity nodes + fact edges), **community subgraph** (label-propagation clusters with map-reduce summaries; names embedded for cosine search). https://arxiv.org/html/2501.13956v1 (§2)
- **Bi-temporal model (the key idea)**: edge carries **valid_at / invalid_at** (when the fact was true in the real world, resolved from relative dates against a reference timestamp t_ref) and **created_at / expired_at** (when the system knew it) — timeline T (world) vs T′ (transaction). On contradiction, an LLM compares the new edge against semantically related existing edges; temporally overlapping contradictions invalidate the old edge by setting its t_invalid to the new edge's t_valid; transactional timeline prioritizes new information. Nothing is deleted; history is preserved. https://arxiv.org/html/2501.13956v1 (§2.2.3)
- **Entity resolution**: extract with last n=4 messages of context + reflexion-style reflection; embed entity name (1024-dim) → cosine + full-text candidates → LLM resolution prompt (is_duplicate, existing uuid, merged full name + summary). Writes use **predefined Cypher, never LLM-generated queries** (schema consistency, less hallucination). https://arxiv.org/html/2501.13956v1 (§2.2.1)
- **Dedup**: edge dedup mirrors entity resolution but the hybrid candidate search is **constrained to edges between the same entity pair** — prevents cross-entity false merges and cuts search space. https://arxiv.org/html/2501.13956v1 (§2.2.2)
- **Communities**: label propagation (not Leiden) chosen for cheap dynamic extension (new node joins the plurality community of neighbors); periodic full refresh still required; drift acknowledged. https://arxiv.org/html/2501.13956v1 (§2.3)
- **Retrieval**: hybrid **cosine (φcos) + Okapi BM25 full-text (φbm25) + n-hop BFS (φbfs)**; BFS can be seeded by recent episodes to pull "recently mentioned" context. Rerankers: RRF, MMR, episode-mentions frequency, node-distance-from-centroid, and cross-encoder (LLM, most expensive). A "constructor" renders facts *with their valid/invalid date ranges* into the context string. BGE-m3 used for embedding + rerank. https://arxiv.org/html/2501.13956v1 (§3, §4.1)
- **DMR benchmark (and its critique)**: Zep 94.8% vs MemGPT 93.4% (gpt-4-turbo); but full-context baseline hits 94.4% (gpt-4-turbo) and 98.0% (gpt-4o-mini) — Zep's own paper calls DMR inadequate: single-turn factoids, ambiguous phrasing, tiny scale (60 messages/conversation). https://arxiv.org/html/2501.13956v1 (§4.2)
- **LongMemEval (headline)**: LongMemEval-S (~115k-token conversations, six question types incl. knowledge-update and temporal-reasoning): retrieve top-20 edges + top-20 entity nodes → **+15.2% (gpt-4o-mini) / +18.5% (gpt-4o) accuracy over full-context, with ~90% latency reduction**; biggest gains on single-session-preference, multi-session, temporal-reasoning; knowledge-update gains only with stronger models — weaker models misread Zep's temporal data. https://arxiv.org/html/2501.13956v1 (§4.3)
- **Infrastructure**: requires a graph DB — Neo4j (Lucene fulltext), FalkorDB (RedisSearch + vecf32), Kuzu, or Amazon Neptune; ships an MCP server with per-group_id graphs; opt-out PostHog telemetry (`GRAPHITI_TELEMETRY_ENABLED=false`); structured-output dependence documented with json_schema/json_object fallback modes for small local models. https://github.com/getzep/graphiti

### 3. Letta / MemGPT (letta-ai/letta) — memory blocks + sleep-time compute

- **Repo/license/activity**: Apache-2.0; 25.0k stars, 2.6k forks, 7,474 commits; last release on main repo v0.16.8 (2026-05-14); **the legacy V1 Python API server is archived** — active development moved to `letta-ai/letta-code` (npm `@letta-ai/letta-code`, TypeScript CLI/agent harness/App Server). https://github.com/letta-ai/letta
- **Taxonomy**: **core memory blocks** (in-context, always visible), **recall memory** (conversation history), **archival memory** (out-of-context store for saved memories). https://www.letta.com/blog/sleep-time-compute
- **Memory blocks & injection**: a block = {label, description, value, limit(chars)}; blocks are prepended to the system prompt in an XML-like `<memory_blocks>` envelope with per-block `chars_current`/`chars_limit` metadata; `persona` and `human` are default labels with autogen'd descriptions; blocks can be read-only, and shared across multiple agents (update once, visible everywhere). Agents edit blocks via built-in memory tools. https://docs.letta.com/guides/agents/memory-blocks
- **Persistence model**: all state — memories, user messages, reasoning, tool calls — is persisted in a database and survives context eviction; core memories are injected into context; the agent self-edits memory through tools. https://docs.letta.com/v1-sdk/concepts/stateful-agents (current docs do not name the DB engine — silence, verify if it matters.)
- **Sleep-time compute (arXiv:2504.13171)**: a "sleep-time enabled agent" is actually **two agents**: a primary (talks to users, has tools, searches recall/archival) **without core-memory edit tools**, and a sleep-time agent that **owns the memory-editing tools for the primary's in-context memory** and its own. Memory management becomes asynchronous; sleep-time transforms "raw context" into "learned context" continuously; the pair can use different models (fast model primary, stronger model at night); runs on a configurable frequency or on context compaction; memory is readable "anytime" while consolidation proceeds; claimed Pareto improvement (latency shifts to idle time) on AIME/GSM. https://www.letta.com/blog/sleep-time-compute
- **Letta Code today (most relevant to us)**: memory is **MemFS — a git-backed memory filesystem** the agent inspects and edits; `/init` bootstraps memory for a project (may ask about working style, may review prior sessions via subagents); `/remember <lesson>` teaches explicitly and commits to MemFS; **`/doctor` audits memory placement, duplication, and system-prompt token usage**; "dreaming" = background subagents reviewing recent conversations and consolidating lessons (runs after N steps or on compaction; optional "agent reviews before applying" second pass); a reorganize workflow backs up the repo before splitting large files/merging duplicates. https://docs.letta.com/letta-agent/memory ; git-based context repositories for coding agents: https://www.letta.com/blog/context-repositories
- **Eval**: MemGPT's DMR 93.4% (gpt-4-turbo, as reported by Zep's paper); Letta could not be evaluated on LongMemEval by the Zep team (no direct ingestion path; archival workaround failed) — a notable integration gap. https://arxiv.org/html/2501.13956v1 (§4.3.1)

### 4. MIRIX (Mirix-AI/MIRIX) — closest published taxonomy to ours

- **Repo/license/activity**: Apache-2.0; 3.5k stars, 274 forks, 383 commits, last commit 2026-08-20; Python 96.3%; built on Letta (acknowledged in README). **Flag**: parent brief said `mirix-research/MIRIX` — that URL 404s; current home is https://github.com/Mirix-AI/MIRIX . Paper arXiv:2507.07957 (CC BY 4.0). https://arxiv.org/abs/2507.07957
- **Taxonomy (six types, concrete schemas)** — https://arxiv.org/html/2507.07957v1 (§3.1):
  - **Core**: persona + human blocks (MemGPT-inspired); when >90% of capacity, a controlled rewrite compacts without losing critical info.
  - **Episodic**: fields event_type (user_message / inferred_result / system_notification), summary, details, actor (user|assistant), timestamp — a structured calendar/log.
  - **Semantic**: name, summary, details, source (user_provided / Wikipedia / inferred); concept/entity knowledge independent of time; visualized as a tree.
  - **Procedural**: entry_type (workflow / guide / script), goal description, steps (optionally JSON) — actionable how-to knowledge.
  - **Resource**: title, summary, resource_type (doc / markdown / pdf_text / image / voice_transcript), full or excerpted content — documents in active use.
  - **Knowledge Vault**: entry_type (credential / bookmark / contact_info / api_key), source, **sensitivity (low/med/high)**, secret_value; high-sensitivity entries access-controlled and **excluded from casual retrieval**.
- **Routing & retrieval**: 8 agents — Meta Memory Manager routes each input to the relevant Memory Managers (one per type) + Chat Agent. **Active Retrieval**: before answering, the agent generates a *topic* from the input, retrieves **top-10 entries from each of the six components**, and injects them into the system prompt wrapped in typed tags (`<episodic_memory>…</episodic_memory>`) so the model knows content and origin. Retrieval functions: `embedding_match`, `bm25_match`, `string_match`. https://arxiv.org/html/2507.07957v1 (§3.2–3.3)
- **Evaluation**: ScreenshotVQA (5k–20k hi-res screenshots/sequence): **+35% over RAG with 99.9% storage reduction; +410% over long-context with 93.3% storage reduction**. LOCOMO: **85.38% overall** (gpt-4.1-mini; runs 83.98/87.34/84.82), "outperforming the best existing method by 8.0%". Baseline table (gpt-4o-mini): Mem0 66.88, Mem0ᵍ 68.44, Zep 75.14, Memobase 70.91, Full-Context 77.51, A-Mem 48.38, LangMem 58.10. https://arxiv.org/html/2507.07957v1 (§1, Appendix A)
- **Conflict flagged in the paper itself**: with gpt-4.1-mini via mem0's harness, Zep scored only 49.09 overall — MIRIX says "we are afraid there might be errors in their implementation" and omits it. Cross-vendor harnesses are not comparable. https://arxiv.org/html/2507.07957v1 (Appendix A)
- **Storage**: Docker images for Postgres, Redis, backend API; packaged app stores memory locally for privacy. https://github.com/Mirix-AI/MIRIX
- **Post-paper evolution (repo)**: per-session `session_tag` routing ("task" → procedural skill distillation only; "conversation" → episodic/semantic extraction); `POST /memory/auto_dream` consolidation endpoint with per-component modes (core/episodic/semantic/resource/procedural/knowledge/experience) and `dry_run`; procedural skills distilled from sessions **including tool calls, errors, retries, and the fix**; ALFWorld SkillOpt 68.7% vs 52.2% no-skill baseline; LOCOMO-10 81.23% on gpt-5.2. https://github.com/Mirix-AI/MIRIX

### 5. Memp — procedural memory evolution

- **Paper**: arXiv:2508.06433 (v4 2026-04-15), ACL 2026 Findings. **Flag**: parent brief said `bytedance/Memp`; the paper links code at `github.com/zjunlp/MemP` (Zhejiang NLP group; ByteDance authors co-author). https://arxiv.org/abs/2508.06433
- **Core design**: distills past agent trajectories into **fine-grained step-by-step instructions AND higher-level script-like abstractions**; systematically studies **Build / Retrieval / Update** strategies for procedural memory; a "dynamic regimen" continuously **updates, corrects, and deprecates** repository contents so it evolves in lockstep with experience. https://arxiv.org/abs/2508.06433
- **Findings**: on TravelPlanner and ALFWorld, refining the repository yields steadily higher success and efficiency on analogous tasks; **memory built by a stronger model transfers — migrating it to a weaker model yields substantial gains**. https://arxiv.org/abs/2508.06433
- **Relevance**: strongest published signal for our procedural layer + auto-skill generation: two granularities (steps vs scripts), explicit deprecation, and model-agnostic transfer.

### 6. MemOS / MemCube (MemTensor/MemOS) — memory-as-OS lifecycle vocabulary

- **Repo/license/activity**: Apache-2.0; 11.7k stars, 1.1k forks, 2,177 commits, latest v2.0.34 (2026-09-23); TypeScript 58.7% / Python 34.2%. Paper arXiv:2507.03724 (v4 2025-12-03, CC BY 4.0). https://github.com/MemTensor/MemOS ; https://arxiv.org/abs/2507.03724
- **Core abstraction**: a **MemCube** is the universal memory unit, encapsulating content + metadata (**provenance, versioning**); MemCubes can be **composed, migrated, and fused**; the system unifies three substrates: **plaintext memory, activation memory (KV-cache), parameter memory**. https://arxiv.org/abs/2507.03724 (abstract)
- **Lifecycle & components**: memory lifecycle = **generation, activation, fusion, archiving, expiration**; orchestrated by MemReader, **MemScheduler**, MemLifecycle, MemOperator; unified Memory API with permission control, scoping, and operation auditing; a layered hierarchy of **working memory / long-term storage / cold archives governed by recency, access frequency, importance**; explicitly attacks "memory islands" (ChatGPT memory can't follow you into Cursor). https://arxiv.org/html/2507.03724v4 (§1)
- **Plaintext memory specifics**: integrated into the inference loop; **high-frequency plaintext can be promoted to activation paths** (externalization/internalization); plaintext stored in a **hierarchical graph organized by task–concept–fact paths**; task parsing + semantic similarity + topic-aware routing for prioritized retrieval; **conflict detection, deduplication, versioning, and forgetting policies**. MemCube organizes semantic fragments into a multi-dimensional structure enabling query-based aggregation and multi-granularity activation. https://arxiv.org/html/2507.03724v4 (§2)
- **Evaluation**: MemOS-1031 reported first on PreFEval, PersonaMem, LongMemEval, and LoCoMo vs MIRIX, Mem0, Zep, Memobase, MemU, Supermemory. https://arxiv.org/html/2507.03724v4 (Fig. 1)
- **Shipped product (repo)**: local plugin is TypeScript, **100% on-device, local-first SQLite**, hybrid retrieval **FTS5 + vector**, "smart dedup", **tiered skill evolution: L1 traces / L2 policies / L3 world model**, multi-agent collaboration; cloud plugins for coding agents (OpenClaw, Hermes, DeepSeek Harness); headline "35.24% token savings". https://github.com/MemTensor/MemOS
- **Adopt the vocabulary, not the architecture**: activation/KV/parameter cubes require model-internal access an agent-side engine doesn't have.

### 7. A-Mem (agiresearch/A-mem) — Zettelkasten dynamic linking

- **Repo/license/activity**: **MIT**; 1.2k stars, 123 forks, 31 commits, no releases, last commit 2025-12-12; Python 100%. Evaluation code separate: `WujiangXu/AgenticMemory`. Paper arXiv:2502.12110 (v11 2025-10-08), NeurIPS 2025. https://github.com/agiresearch/A-mem ; https://arxiv.org/abs/2502.12110
- **Design**: each memory becomes a note with structured attributes (**contextual description, keywords, tags**, timestamp); on insert, embed and retrieve related historical notes, then an LLM establishes links by similarity/shared attributes; **memory evolution** — new memories trigger updates to existing notes' context and attributes, so the network refines continuously (Zettelkasten principles). https://arxiv.org/abs/2502.12110 ; https://github.com/agiresearch/A-mem
- **Storage/retrieval**: ChromaDB vector store; `add_note/read/search_agentic/update/delete`; OpenAI or Ollama backends. https://github.com/agiresearch/A-mem
- **Temporal handling**: timestamps only; no validity/invalidity model (silence).
- **Evaluation**: "six foundation models," superior vs SOTA baselines (paper abstract); third-party reruns are much less flattering — Mem0 reports A-Mem lags >25 J points (https://arxiv.org/html/2504.19413v1 §4.1); MIRIX's table has A-Mem 48.38 overall (gpt-4o-mini) (https://arxiv.org/html/2507.07957v1 Appendix A).
- **Maintenance**: effectively dormant since Dec 2025 — treat as a paper artifact, not infra to depend on. https://github.com/agiresearch/A-mem

### 8. cognee (topoteretes/cognee) — knowledge-graph pipeline, Postgres full-stack

- **Repo/license/activity**: Apache-2.0; 31.3k stars, 3.2k forks, 10,984 commits, latest v1.6.2 (2026-09-29), 307 contributors; Python 86.7% / TS 11.7%. https://github.com/topoteretes/cognee
- **Pipeline**: `cognee.remember(...)` / `add` → **`cognify()`** (chunking → entity/edge extraction → ontology grounding → community summarization) → hybrid search; deletion via `datasets.delete_data`. The brand name for the pipeline is ECL (Extract–Cognify–Load) — **flag**: the fetched README sections did not surface the acronym (truncation); verify on docs.cognee.com before citing in an ADR. https://github.com/topoteretes/cognee
- **Ontology grounding (opt-in)**: default `annotate` canonicalizes/enriches and is byte-identical; `ONTOLOGY_MODE=strict` drops extracted entities with neither a class match on type nor an individual match on name, and filters edges touching dropped nodes (chunk text still stored/embedded). https://github.com/topoteretes/cognee (PR #4848)
- **Postgres full-stack (key data point)**: "Since cognee 1.0 you can run the entire memory layer on a single Postgres instance" — relational metadata + PGVector + graph state in one Postgres service. **OSS boundary flag**: shipped as a *demo feature*; "the production-ready version is available as a licensed product." https://github.com/topoteretes/cognee
- **Local-first AI**: v1.6.0 (2026-09-18) added keyless workflows — build and search text memory with local models and no cloud LLM key; LLM-dependent improvement stages skip when no LLM is configured; pipeline recovery preserves completed documents after crashes. https://github.com/topoteretes/cognee/releases/tag/v1.6.0
- **Code memory**: a codegraph pipeline exists in-repo (source-code chunking, code summarization, SWE-bench retrieval experiments). https://github.com/topoteretes/cognee (commit history)
- **Evaluation**: BEAM framework in-repo: **0.79 @ 100K-token context, 0.67 @ 10M**, with explicit methodology caveats ("read the REPORT.md before comparing with other systems"); also Slack-history sync, Google Drive/Gmail connectors, MCP server (`cognee-mcp`). https://github.com/topoteretes/cognee
- **Research backing**: arXiv:2505.24478 "Optimizing the Interface Between Knowledge Graphs and LLMs for Complex Reasoning." https://arxiv.org/abs/2505.24478

### 9. Skim: MemAgent (RL-based memory management)

MemAgent (arXiv:2507.02259, ICLR 2026 Oral; Tsinghua AIR + ByteDance Seed) trains an agent with RL (extended DAPO, independent-context multi-conversation generation) to **read text in segments and overwrite a fixed-length memory after each segment**: an 8K-context model trained on 32K text extrapolates to a **3.5M-token QA task with <5% performance loss, and 95%+ on 512K RULER**. https://arxiv.org/abs/2507.02259 ; https://memagent-sialab.github.io/ . Takeaway: learned fixed-size overwrite memory can rival full-context — but it requires a *trained model*, not tool-called infrastructure; not directly applicable to onememory, though it argues hard for strict memory budgets at retrieval time.

### 10. Skim: memU (NevaMind-AI/memU) — agent-authored wiki + host adapters

memU (Apache-2.0; 14.5k stars; Python 99.6%; latest release v1.5.1, 2026-03-23) stores memory as an **agent-editable wiki** across sessions/agents/devices, with core memory logic "only 500 lines". https://github.com/NevaMind-AI/memU . Host adapters ship one binary per coding agent (Codex, Claude Code, Cursor, OpenClaw, Hermes, WorkBuddy, Cola, pi), each mining that agent's **session logs** (JSONL/SQLite, read-only) and patching its **instruction file** (AGENTS.md / CLAUDE.md / SOUL.md / MEMORY.md) — two seams: "record" and "inject"; `memu-agent detect` sniffs unknown hosts. **Automatic skill extraction**: a scheduled task slices new sessions into self-contained jobs; *the agent itself* decides to do nothing / patch / create a skill and writes readable Markdown (name, description, reusable workflow, edge cases, pitfalls); `commit` embeds name+description and stores under the "skill" track. Crucially, **MemoryService makes no LLM calls** — judgment stays in the agent. Storage: SQLite (brute-force cosine), in-memory, or **Postgres + pgvector**. https://github.com/NevaMind-AI/memU

## What onememory should adopt

Mapped to our lifecycle (observe→ingest→normalize→extract→classify→dedupe→entity-resolve→score→store→retrieve→reinforce→consolidate→decay→archive) and our ten layers.

1. **Bi-temporal columns on every memory row** (Zep): `valid_at`/`invalid_at` (fact truth in the world) + `created_at`/`expired_at` (system knowledge). Contradiction ⇒ **invalidate, never delete** (Zep §2.2.3; Mem0ᵍ does the same for graph edges). Feeds store, reinforce, decay, archive. Cite: https://arxiv.org/html/2501.13956v1
2. **Two-phase extract-then-resolve write loop** (Mem0 paper): candidate facts → compare against top-s semantically similar memories → explicit ADD/UPDATE/DELETE/NOOP decision; UPDATE only when new information content exceeds the old (Algorithm 1). But run it **off the hot path** — Mem0's own 2026 production algorithm went single-pass ADD-only, and Letta/MIRIX both push consolidation to background agents (sleep-time; auto-dream; ~60s batch cadence in MIRIX's app). Recommended shape: write-time cheap classify+dedupe, contradiction resolution deferred to consolidate. Cite: https://arxiv.org/html/2504.19413v1 ; https://www.letta.com/blog/sleep-time-compute
3. **Per-type schemas from MIRIX** as the schema baseline for our ten layers: episodic = {event_type, summary, details, actor, timestamp}; semantic = {name, summary, details, source}; procedural = {entry_type, goal, steps}; working ≈ MIRIX core (capacity % + controlled rewrite at 90%); source ≈ MIRIX resource ({title, summary, resource_type, content}); preference ≈ sensitivity-tagged core/semantic hybrid. Cite: https://arxiv.org/html/2507.07957v1 (§3.1)
4. **Active Retrieval with per-type routing** (MIRIX): auto-generate a topic/plan per turn, retrieve top-k **per layer**, inject with typed tags and (Zep) validity date ranges; budget-aware (Zep retrieves top-20 edges + 20 nodes; Mem0 uses top-200 budget). This is the retrieval half of our token-budgeted hybrid design. Cite: https://arxiv.org/html/2507.07957v1 (§3.2) ; https://arxiv.org/html/2501.13956v1 (§4)
5. **Hybrid multi-signal retrieval + fused ranking** (Mem0 2026, Zep, MIRIX): semantic (pgvector) + BM25/FTS5 + entity-match signals scored in parallel and fused; optional graph-expansion (Zep BFS seeded by recent episodes) and optional cross-encoder rerank behind a cost flag (Zep marks cross-encoders most expensive). Cite: https://github.com/mem0ai/mem0 ; https://arxiv.org/html/2501.13956v1 (§3.2)
6. **Entity resolution as its own lifecycle stage** (Zep): cosine + full-text candidates, LLM resolves duplicates with merged name/summary; **constrain edge/fact dedup to the same entity pair** to prevent cross-entity false merges; entity linking then boosts retrieval (Mem0 2026). Feeds our entity-resolve + dedupe stages. Cite: https://arxiv.org/html/2501.13956v1 (§2.2)
7. **Sleep-time consolidation as an engine primitive** (Letta + MIRIX): background job owns memory mutation tools (primary agent never edits on the hot path), configurable frequency or on-compaction trigger, per-component modes with `dry_run` (MIRIX auto_dream), review-before-apply option (Letta dreaming), and stronger-model-at-night split (Letta). Feeds reinforce/consolidate/decay. Cite: https://www.letta.com/blog/sleep-time-compute ; https://github.com/Mirix-AI/MIRIX
8. **Procedural/failure layers with two granularities + deprecation** (Memp + MIRIX + memU + MemOS): distill trajectories into step-level and script-level skills; mine **tool errors, retries, and the fix that worked** as first-class failure-layer signals (MIRIX skill distillation; ALFWorld 68.7% vs 52.2%); agent-authored Markdown skills that get committed, embedded, and retrieved (memU); tiered evolution L1 traces → L2 policies → L3 world model (MemOS local plugin); explicit correction/deprecation lifecycle (Memp). This is the published foundation for our procedural, failure, and auto-skill-generation features. Cite: https://arxiv.org/abs/2508.06433 ; https://github.com/NevaMind-AI/memU ; https://github.com/MemTensor/MemOS
9. **Git-keyed code/project memory** (Letta MemFS + memU): memory as inspectable, git-versioned files; `/init` bootstrap, explicit `/remember` teach, **`/doctor` audit of placement/duplication/token-usage** as UX verbs; memU's two integration seams (mine session logs = record; patch AGENTS.md/CLAUDE.md = inject) define exactly how a sidecar memory engine attaches to Claude Code/Codex/Cursor/pi without cooperation from the agent binary. Validates our git-fingerprint project layer. Cite: https://docs.letta.com/letta-agent/memory ; https://github.com/NevaMind-AI/memU
10. **Postgres+pgvector single-store** (Mem0 self-hosted + cognee + memU): all three ship Postgres+pgvector as the self-hosted path; cognee even runs relational+vector+graph state in one Postgres (albeit demo vs licensed split — we should keep this fully open). Supports our Docker-Postgres default and the PGlite embedded evaluation; avoids Zep's mandatory Neo4j/FalkorDB. Cite: https://docs.mem0.ai/open-source/overview ; https://github.com/topoteretes/cognee
11. **MemOS lifecycle vocabulary for our decay/archive stages**: explicit states (active/archived/expired) + provenance + versioning on every row; hot/warm/cold promotion governed by recency, access frequency, importance (MemOS working/long-term/cold archives; MemoryBank's strengthen-on-recall/decay-over-time is described in Mem0's paper appendix as the human-mimicking pattern). Cite: https://arxiv.org/html/2507.03724v4 ; https://arxiv.org/html/2504.19413v1 (Appendix C)
12. **Ops surface**: CLI (`mem0 init/add/search`), MCP server with per-group/user scoping (Graphiti), self-hosted REST with per-user API keys + request audit log + async memory + metadata filters (Mem0 OSS server), per-user/scope read/write filters on every memory table (MIRIX's `filter_tags`/scope enforcement). Cite: https://github.com/mem0ai/mem0 ; https://github.com/getzep/graphiti ; https://docs.mem0.ai/open-source/overview ; https://github.com/Mirix-AI/MIRIX
13. **Evaluation discipline** (Mem0's dual metrics): always report per-question-type LLM-as-Judge **plus** deployment metrics (retrieved tokens, p95 search/total latency) over ≥10 runs; use LOCOMO + LongMemEval as primary, BEAM for 100K–10M scale (cognee); publish a reproducible OSS harness (Mem0 open-sourced memory-benchmarks for this). Cite: https://arxiv.org/html/2504.19413v1 (§3.2) ; https://github.com/topoteretes/cognee

## What to avoid

1. **DMR as a headline benchmark** — Zep's own paper dissects it: single-turn factoids, ambiguous phrasing, ~60 messages, and full-context nearly ties the best memory system. https://arxiv.org/html/2501.13956v1 (§4.2)
2. **LOCOMO-only SOTA claims** — avg ~9k tokens/conversation means full-context is nearly the upper bound (MIRIX: full-context 77.51 on gpt-4o-mini, 88.13 on gpt-4.1-mini; and their 85.4 beats every memory system but not full-context). Cross-vendor harnesses also disagree wildly (Zep = 75.14 in MIRIX's gpt-4o-mini run vs 49.09 via the mem0 harness on gpt-4.1-mini — flagged by MIRIX as a probable harness bug). https://arxiv.org/html/2507.07957v1
3. **Inline LLM UPDATE/DELETE in the hot path** — Mem0's production algorithm dropped UPDATE/DELETE for single-pass ADD-only, and Zep/Mem0ᵍ avoid destructive deletes entirely; a wrong DELETE destroys history irrecoverably. https://github.com/mem0ai/mem0
4. **A hard graph-database dependency** — Graphiti requires Neo4j/FalkorDB/Kuzu/Neptune; that is a heavy install for a local-first coding tool, and Mem0's 2026 pivot (entity linking + hybrid retrieval, graph deprioritized) plus cognee's Postgres-graph demo suggest a relational projection suffices at our scale. https://github.com/getzep/graphiti
5. **One flat memory store** — MIRIX's opening critique of Letta/Mem0/ChatGPT (no compositional structure, poor routing). We have ten layers; keep retrieval per-type. https://arxiv.org/html/2507.07957v1 (§1)
6. **A standing LLM-in-the-engine per ingest** — memU's design principle ("MemoryService makes no LLM calls"; judgment stays in the agent) plus Mem0's async summary module and MIRIX's 60s batching all point the same way: batch, background, or delegate. https://github.com/NevaMind-AI/memU
7. **Eight separate agents to manage memory** (MIRIX) — heavy for a self-hosted CLI product; implement per-type managers as prompt stages/policies inside one engine, not as independent agents.
8. **Storing raw secrets by default** (MIRIX Knowledge Vault with api_key/credential values) — for a coding-agent memory engine this is a liability; prefer detect-and-redact with a pointer to the OS keychain, or an explicit, off-by-default vault. https://arxiv.org/html/2507.07957v1 (§3.1)
9. **Default-on telemetry** — Graphiti ships opt-out PostHog analytics; for a local-first, privacy-positioned product, telemetry must be opt-in. https://github.com/getzep/graphiti
10. **Licensed "production" splits of core functionality** — cognee's Postgres graph store is a demo in Apache-2.0 with the production version licensed; Mem0's best benchmark numbers are platform-only. onememory's differentiator is that the whole loop, at full fidelity, is Apache-2.0. https://github.com/topoteretes/cognee ; https://github.com/mem0ai/mem0
11. **Activation/KV/parameter memory cubes** (MemOS) — they require model-internal access (KV injection, steering vectors); borrow the lifecycle/provenance/versioning vocabulary only. https://arxiv.org/html/2507.03724v4
12. **Learned-overwrite memory** (MemAgent) — requires an RL-trained model; incompatible with a provider-agnostic, tool-called memory engine. https://arxiv.org/abs/2507.02259

## Open questions

1. **OpenMemory MCP status** — third-party sources describe it as Mem0's retired/earlier local-first deployment (DeepWiki; ContextBolt reports one mem0 MCP archived); the current README is silent. Verify directly before writing our MCP server ADR. https://contextbolt.com/blog/mem0-mcp/
2. **Mem0 OSS-vs-platform parity** — 92.5 LOCOMO / 94.4 LongMemEval are managed-platform numbers ("proprietary optimizations not available in the open-source SDK"); how much of the 2026 algorithm actually ships in Apache-2.0 `mem0` is unstated. https://github.com/mem0ai/mem0
3. **Letta's current storage engine** — current docs say state is "persisted in a database" and memory files are git-backed (MemFS), but the fetched pages never name the DB engine; the legacy Postgres server is archived. Verify if Letta remains a reference for storage schema. https://docs.letta.com/letta-agent/memory
4. **Memp code home** — paper links `github.com/zjunlp/MemP`; parent brief said `bytedance/Memp`. Verify the org before citing. https://arxiv.org/abs/2508.06433
5. **cognee ECL naming** — "Extract-Cognify-Load" did not surface in the fetched README sections (truncation); confirm the canonical pipeline name/structure on docs.cognee.com. https://github.com/topoteretes/cognee
6. **Graph projection vs pure relational** — do we need any graph edges at all, or do Postgres entity/relation tables + recursive CTEs + pgvector cover our retrieval? Evidence: Zep needs Cypher; Mem0 moved to entity-linking + hybrid fusion without a graph-first store; cognee proves graph state can live in Postgres. Needs a spike.
7. **Secrets policy for preference/source layers** — MIRIX stores secrets with sensitivity tiers; do we redact-and-point instead? Needs a decision before schema freeze. https://arxiv.org/html/2507.07957v1 (§3.1)
8. **Unanswerable-question handling** — Mem0 excluded LOCOMO's adversarial category for lack of ground truth; our failure layer could own "recognize unanswerable" as a scored behavior. Design an eval for it. https://arxiv.org/html/2504.19413v1 (§3.1)
9. **BEAM reproduction** — cognee publishes BEAM (0.79@100K / 0.67@10M) with a methodology report; Mem0 reports BEAM-1M/10M too. Adopting BEAM for our scale claims requires reproducing their harness. https://github.com/topoteretes/cognee
10. **Cross-model skill transfer** — Memp shows procedural memory built by a stronger model transfers to weaker models; our auto-generated skills should be validated model-agnostic (prose, not model-specific tokens). https://arxiv.org/abs/2508.06433
11. **License asymmetry** — Zep's *paper* is CC BY-NC-SA (code Apache-2.0); A-Mem is MIT; everything else Apache-2.0. If we quote paper text or figures in docs, respect the paper licenses. https://arxiv.org/abs/2501.13956
12. **Benchmark conflict adjudication** — every system's self-reported LOCOMO/LongMemEval run beats every other system (Mem0 92.5 > MemOS > MIRIX 85.4 > Zep 75.1 > Mem0-paper 66.9, all "LOCOMO overall", all with different judges/models/harnesses). Any onememory number must state judge model, harness, and retrieval budget or it will be noise. https://arxiv.org/html/2507.07957v1 (Appendix A)
